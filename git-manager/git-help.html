Synchronisation

Remote (origin)
L'adresse du dépôt distant (GitHub). Lie votre dépôt local à GitHub pour synchroniser vos fichiers. Sans remote, pas de Push/Pull possible.
Push
Envoie vos commits locaux vers GitHub. Vos modifications deviennent visibles pour tous.
Pull
Récupère les dernières modifications depuis GitHub et les fusionne avec votre code local.
Fetch
Vérifie s'il y a des nouveautés sur GitHub sans modifier vos fichiers locaux.
Vous créez une nouvelle branche sur Github, ensuite Fetch et bouton elle apparaîtra en branche distante.
Option --rebase (Pull)
Quand vous avez des commits locaux et des commits distants, git pull crée un commit de fusion (merge). Avec --rebase, vos commits locaux sont rejoués après les commits distants, sans merge commit :
Sans rebase (merge) :
distant : A --- B --- C
local  : A --- B --- D
résultat: A --- B --- C --- D --- M (merge commit en plus)
Avec --rebase :
distant : A --- B --- C
local  : A --- B --- D
résultat: A --- B --- C --- D' (D rejoué après C, pas de merge)
Ordre important : Toujours Pull avant Push, avec ou sans rebase. Si le dépôt distant contient des commits que vous n'avez pas, Git refusera le Push. L'option --rebase change la manière dont Pull intègre les commits, pas l'ordre des opérations.
Recommandé pour un usage personnel : historique propre et linéaire, pas de merge commits inutiles.

Statuts des fichiers

M Modifié
Fichier déjà suivi par Git dont le contenu a changé depuis le dernier commit. Cochez-le et faites un commit pour enregistrer les modifications.
A Ajouté (stagé)
Fichier dont les modifications ont été placées dans la zone de staging (l'index Git), prêt à être inclus dans le prochain commit. Peut être un nouveau fichier ou un fichier modifié explicitement stagé via le bouton Stager.
D Supprimé
Fichier qui existait dans le dernier commit mais qui a été supprimé. Le commit enregistrera cette suppression dans l'historique.
U Non suivi
Fichier présent sur le disque mais inconnu de Git. Il ne sera pas inclus dans les commits tant que vous ne le cochez pas. Vous pouvez aussi l'ajouter au .gitignore pour l'ignorer définitivement.
Zone de staging (index)
La zone de staging est une zone intermédiaire entre vos fichiers et l'historique Git. Elle permet de choisir exactement ce qui entre dans le prochain commit, indépendamment de ce qui est modifié sur le disque.
Dans git-manager, le bouton Commit fait automatiquement git add sur les fichiers cochés — vous n'avez pas besoin de stager explicitement avant de commiter. Le bouton Stager est utile dans un cas précis : préparer un fichier pour un Amend sans commiter tout de suite.
Cas AM — si vous stagez un fichier puis le modifiez à nouveau sans commiter, il apparaît en A et M simultanément. Le prochain Commit inclura les deux zones ensemble — il n'est pas possible de les séparer.
Fichiers suivis
Le compteur Suivis dans le statut indique le nombre total de fichiers versionnés par Git. Ce sont les fichiers qui ont été committés au moins une fois et dont Git surveille les modifications.
Arrêter le suivi
Retirer un fichier du suivi Git le conserve sur le disque mais Git ne le versionne plus. Utile pour les fichiers de configuration locale.

Diff visuel

Cliquer sur un nom de fichier
Dans la section Fichiers modifiés — Diff & Commit, les fichiers M A D ont leur nom souligné et cliquable. Cliquer ouvre une modale avec les modifications ligne par ligne.
Les fichiers U ne sont pas cliquables — Git n'a rien à comparer.
Lecture du diff
Le tableau affiche 3 colonnes : numéro de ligne dans l'ancien fichier, numéro dans le nouveau, et le contenu.
Format d'une ligne :
12 12   ligne inchangée
13 − ancienne ligne
13 + nouvelle ligne
En-tête de bloc (hunk) :
@@ -97,6 +97,24 @@ switch ($action) {
-97,6 → ancien fichier : bloc à partir de la ligne 97, sur 6 lignes
+97,24 → nouveau fichier : même départ, sur 24 lignes (18 ajoutées)
switch ($action) { → contexte : le bloc de code englobant
Fichiers M et A — deux onglets possibles
Un fichier M ou A peut avoir des modifications dans deux zones :
Non stagé Modifications depuis le dernier git add — sera stagé au prochain Stager
Stagé Sera inclus dans le prochain Commit
Si les deux zones sont remplies, deux onglets apparaissent dans la modale.
Exemple pour obtenir les deux onglets :
1. Modifiez index.html et enregistrez
2. Cliquez Stager → le fichier passe en A
3. Modifiez à nouveau index.html et enregistrez — sans restager
4. Actualisez → le fichier apparaît en A et en M
5. Cliquez sur M → deux onglets Non stagé / Stagé
6. Cliquez sur A → deux onglets Non stagé / Stagé

Récupération

HEAD
La version actuelle (dernier commit).
HEAD~1
La version du commit précédent.
HEAD~2
La version d'il y a 2 commits.
origin/main
La version sur GitHub (serveur distant).
4 façons de revenir en arrière :
Récupérer Restaure 1 fichier à une version précise Reste sur la branche
Checkout commit Explorer un ancien commit (tout le projet) HEAD détaché
Revert Annule un commit en créant un nouveau commit inverse N'écrase pas l'historique
Annuler tout Remet tous les fichiers modifiés au dernier commit Irréversible
Revert vs Checkout :
A → B → C → D  (main)
git checkout B → tu vois le code au moment de B, mais D existe toujours
git revert D → crée un commit E qui annule D :
A → B → C → D → E  (main)
git revert d'un revert → annule l'annulation (équivalent Ctrl+Y) :
A → B → C → Revert "C" → Revert "Revert C"
En cas de doute, utilisez le Stash pour sauvegarder vos modifications avant de revenir en arrière.

Avance / Retard

↑ Commits en avance
Commits locaux non encore envoyés sur GitHub. → Faire un Push
↓ Commits en retard
Commits sur GitHub non encore récupérés. → Faire un Pull
ex. 2 en avance :
PC: A→B→C→D→E
GitHub: A→B→C
ex. 2 en retard :
PC: A→B→C
GitHub: A→B→C→D→E
ex. Cas mixte (après un fetch ↑1 ↓2) :
PC: A→B→C→X
GitHub: A→B→C→Y→Z
→ Pull puis Push

Stash (Mettre de côté)

Mettre de côté
Sauvegarde temporairement vos modifications en cours sans faire de commit. Utile pour changer de branche rapidement ou tester quelque chose sur un code propre.
Pop (Restaurer)
Réapplique les modifications sauvegardées et supprime le stash. C'est l'action la plus courante.
Appliquer
Réapplique les modifications sauvegardées mais conserve le stash pour une utilisation ultérieure.
Supprimer un stash
Supprime définitivement un stash. Les modifications sauvegardées seront perdues.
Exemple :
1. Vous travaillez sur une feature, code pas fini
2. Urgence : corriger un bug sur main
3. Mettre de côté → vos modifications sont sauvegardées
4. Basculer sur main, corriger, commit, push
5. Revenir sur votre branche → Pop
6. Vos modifications sont de retour !

Tags

Tag léger
Simple pointeur vers un commit. Créé sans message. Utile pour un repère personnel.
Tag annoté
Objet Git à part entière avec un message, une date et l'auteur du tag. Recommandé pour les releases.
Push
Envoie le tag vers GitHub. Sans push, le tag reste local et n'est pas visible dans les releases GitHub. Pousser un tag déjà publié est sans effet.
Supprimer
Supprime le tag localement et tente automatiquement de le supprimer sur GitHub. Si le tag n'avait jamais été pushé, la suppression distante est ignorée silencieusement.
Convention MAJOR.MINOR.PATCH
· PATCH (+0.0.1) : correction de bug ou petit ajustement
· MINOR (+0.1.0) : nouvelle page ou fonctionnalité
· MAJOR (+1.0.0) : refonte architecturale ou visuelle importante
Créer une release pour un jalon significatif, pas pour chaque petit fix.

Actions dangereuses

Annuler toutes les modifications
Supprime TOUTES les modifications non committées. Irréversible !
Supprimer (dépôt + disque)
Supprime le fichier du dépôt ET de votre disque. Définitif !

Amend (modifier le dernier commit)

Bouton Amend
Modifie le dernier commit. Vous pouvez l'utiliser pour trois choses, seules ou combinées :
  • Ajouter des fichiers oubliés (cochez-les avant de cliquer Amend)
  • Changer le message (saisissez-en un nouveau dans le champ message avant de cliquer Amend)
  • Inclure des fichiers déjà stagés (ils sont pris automatiquement, sans avoir à les re-cocher)
Charger le message du dernier commit
Dans la section Historique des commits, le premier commit affiche un bouton crayon . Cliquez dessus pour charger le message complet (sujet et corps) dans le champ message — le champ prend le focus automatiquement. Modifiez-le, puis cliquez Amend.
Utile pour corriger une faute ou compléter la description sans retaper tout le message.
Commandes exécutées selon le cas :
# Ajouter un fichier oublié (sans changer le message)
git add fichier.txt
git commit --amend --no-edit
# Changer uniquement le message
git commit --amend -m "Nouveau message"
# Les deux à la fois
git add fichier.txt
git commit --amend -m "Nouveau message"
Exemples :
• Vous committez "Ajout du formulaire de contact" en oubliant style.css → cochez style.css et cliquez Amend
• Vous constatez une faute dans le message du dernier commit → corrigez-le dans le champ message et cliquez Amend (sans rien cocher)
• Vous avez déjà stagé un fichier via le bouton Stager → cliquez Amend directement, il est inclus automatiquement
• Vous voulez compléter le message du dernier commit sans tout retaper → cliquez dans l'Historique, modifiez le champ, puis cliquez Amend
Attention : L'amend réécrit le commit (nouveau hash). Si ce commit a déjà été pushé sur le remote, un git push --force sera nécessaire pour écraser l'ancien commit sur GitHub — l'interface vous en avertit automatiquement. À utiliser de préférence avant le Push, et uniquement sur une branche personnelle non partagée.

Fusionner (Merge)

Bouton Fusionner
Le bouton bleu apparaît à côté des branches qui ne sont pas la branche courante.
Que fait le merge ?
Il intègre les commits de la branche sélectionnée dans la branche courante.
Exemple :
Vous êtes sur main
Vous cliquez sur feature
→ Les commits de feature sont ajoutés à main
Workflow : Basculer sur main → Merge de feature → Push
Conflits de fusion
Si le même fichier a été modifié sur les deux branches :
Lignes différentes → Git fusionne automatiquement
Mêmes lignes → Conflit ! Git marque le fichier :
<<<<<<< HEAD
Code sur main
=======
Code sur feature
>>>>>>> feature
Résolution :
1. Ouvrir le fichier et choisir quelle version garder
2. Supprimer les marqueurs <<<, ===, >>>
3. Sauvegarder → Commit

Fork (contribution)

Qu'est-ce qu'un fork ?
Une copie d'un dépôt GitHub vers votre propre compte. Permet de contribuer à un projet sans avoir les droits d'écriture ou créer votre propre version, le fork devient votre point de départ indépendant.
Dépôt original (autre utilisateur)
↓ Fork (sur GitHub)
Votre fork (votre compte GitHub)
↓ Clone
Votre PC (travail local)
↓ Push
Votre fork
↓ Pull Request
Dépôt original (proposition)
Le fork se fait sur GitHub.com (bouton "Fork"). Utilisez ensuite Cloner un dépôt pour récupérer votre fork.

Gestion des branches

Récupérer une branche distante
Cliquer sur une branche distante crée automatiquement une branche locale qui suit la branche distante.
Supprimer une branche distante
Le bouton poubelle à côté des branches distantes permet de les supprimer directement sur GitHub.
Forcer le basculement
Si des fichiers non suivis bloquent le changement de branche, une option "Forcer" est proposée. Attention : les fichiers en conflit seront écrasés.
Renommer une branche
Le crayon permet de renommer une branche. Si la branche est publiée sur le remote, Git Manager renomme localement, publie le nouveau nom et supprime l'ancien automatiquement.
La branche par défaut (main ou master) ne peut pas être renommée car c'est la branche principale du dépôt distant.
Créer une branche :
Branche actuelle Copie avec historique
🆕 Branche vide Sans fichiers, sans historique
🔄 Nouveau départ Fichiers actuels, sans historique
Autre branche Copie d'une branche spécifique

HEAD détaché

Qu'est-ce que le HEAD détaché ?
Normalement, vous êtes toujours sur une branche (ex: main). Le HEAD détaché signifie que vous vous êtes placé directement sur un ancien commit, sans être sur aucune branche. C'est un mode d'exploration temporaire.
Se placer sur un commit
Dans l'historique des commits, cliquez sur le bouton à droite d'un commit pour vous y placer. Vous verrez vos fichiers tels qu'ils étaient à ce moment-là.
Créer une branche ici
Si le code vous convient, cliquez sur Créer une branche ici pour transformer cet état en branche officielle. Vous pourrez ensuite la fusionner où vous voulez.
Exemple de workflow :
1. Vous explorez l'historique et trouvez un ancien commit intéressant
2. Vous cliquez → Vous êtes en HEAD détaché
3. Vous vérifiez le code : il est parfait !
4. Vous cliquez Créer une branche ici → ex: ma-version
5. Maintenant ma-version est une branche officielle
6. Vous pouvez la fusionner dans main ou la publier sur GitHub
Pour revenir à la normale, basculez simplement sur une branche existante (ex: main).

Multi-dépôts

Sélecteur de dépôt
Menu déroulant affiché dans le header à côté du nom du dépôt courant. Permet de basculer entre plusieurs projets Git sans changer de virtual host.
Activation du sélecteur
Définir la clé reposRoot dans git-config.php avec le chemin absolu du dossier contenant vos projets. Si la clé est absente ou vide, le sélecteur n'est pas affiché.
Configuration dans git-config.php :
'reposRoot' => 'C:/Users/votre-nom/projets',
Structure attendue :
projets/
  ├── mon-site/ <- affiché dans le menu
  │ └── .git/
  ├── api-projet/ <- affiché dans le menu
  │ └── .git/
  └── dossier-sans-git/ <- ignoré
Seuls les sous-dossiers directs contenant un .git/ sont listés.
Si vous déplacez votre dossier de projets, pensez à mettre à jour le chemin reposRoot dans git-config.php.

Cloner un dépôt

Page de clonage
Permet de cloner un dépôt GitHub existant vers votre machine. Les fichiers Git Manager sont automatiquement copiés dans le nouveau dépôt.
Fichiers copiés :
git-manager.html, git-api.php, git-config.example.php, git-clone.html, git-reset-remote.html, git-auth.html, git-help.html, index.html, flavicon.svg
Sous-dossiers copiés intégralement : api/, css/, js/
Mise en service du dépôt cloné :
  1. Renommer git-config.example.php en git-config.php et renseigner identité Git et chemin SSH.
  2. Créer un virtual host Apache pointant vers le dossier cloné.
  3. Accéder à http://[nom-du-projet]/git-manager/git-manager.html.
Ouvrir le dossier via l'Explorateur Windows (file://) ne fonctionnera pas — PHP doit être exécuté par Apache.

Réinitialiser le dépôt distant

Page de réinitialisation
Crée une nouvelle branche vide (sans historique) et supprime les branches sélectionnées sur GitHub. Irréversible !

Retirer un fichier du dernier commit (avant push)

Le fichier est dans le dernier commit mais le push n'a pas encore été fait — l'amend est la solution propre.

  1. Section Supprimer un fichier du dépôt → sélectionner le fichier
  2. Cliquer Arrêter le suivi uniquement (conserve le fichier sur le disque) ou Supprimer (supprime aussi du disque)
  3. Le fichier apparaît en D dans la liste des fichiers modifiés
  4. Cocher le fichier, laisser le champ message vide, cliquer Amend
Le fichier est retiré du dernier commit sans créer un nouveau commit. Le message du commit original est conservé.

Statut A et M simultanés sur le même fichier

Vous stagez un fichier, puis vous le modifiez à nouveau sans commiter. Git suit deux états séparément — le fichier apparaît deux fois.

A Staging La version stagée — celle qui sera commitée si vous commitez maintenant
M Working tree La version actuelle sur disque — avec les nouvelles modifications
Si vous commitez maintenant, les modifications du working tree ne seront pas incluses — seule la version A partirait dans le commit.
Pour inclure les dernières modifications, il faut re-stager le fichier (bouton Stager ou git add), ce qui écrase le A avec le contenu actuel.

Workflow typique

  1. Modifier vos fichiers dans votre éditeur de code
  2. Vérifier les changements dans la section "Fichiers modifiés" — vos fichiers apparaissent avec le statut M (modifié), A (ajouté) ou U (non suivi) ou D (supprimé).
  3. Cocher les fichiers à inclure dans le commit — le git add se fait automatiquement au moment du commit
  4. Écrire un message clair décrivant les changements (ex: "Ajout du formulaire de contact")
  5. Commit pour enregistrer un instantané de vos fichiers stagés dans l'historique local
  6. Push pour envoyer vos commits vers GitHub et les partager
Bon à savoir :
  • Fetch avant de travailler pour récupérer les dernières modifications distantes
  • Pull pour fusionner les modifications distantes dans votre branche locale
  • Un commit reste local tant que vous n'avez pas fait de Push
