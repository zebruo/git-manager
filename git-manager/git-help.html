Synchronisation

Remote (origin)
L'adresse du dépôt distant (GitHub). Lie votre dépôt local à GitHub pour synchroniser vos fichiers. Sans remote, pas de Push/Pull possible.
Push
Envoie vos commits locaux vers GitHub. Vos modifications deviennent visibles pour tous.
Pull
Récupère les dernières modifications depuis GitHub et les fusionne avec votre code local.
Fetch
Vérifie s'il y a des nouveautés sur GitHub sans modifier vos fichiers locaux.
Vous créez une nouvelle branche sur Github, ensuite Fetch et bouton elle apparaîtra en branche distante.
Option --rebase (Pull)
Quand vous avez des commits locaux et des commits distants, git pull crée un commit de fusion (merge). Avec --rebase, vos commits locaux sont rejoués après les commits distants, sans merge commit :
Sans rebase (merge) :
distant : A --- B --- C
local  : A --- B --- D
résultat: A --- B --- C --- D --- M (merge commit en plus)
Avec --rebase :
distant : A --- B --- C
local  : A --- B --- D
résultat: A --- B --- C --- D' (D rejoué après C, pas de merge)
Ordre important : Toujours Pull avant Push, avec ou sans rebase. Si le dépôt distant contient des commits que vous n'avez pas, Git refusera le Push. L'option --rebase change la manière dont Pull intègre les commits, pas l'ordre des opérations.
Recommandé pour un usage personnel : historique propre et linéaire, pas de merge commits inutiles.

Statuts des fichiers

M Modifié
Fichier déjà suivi par Git dont le contenu a changé depuis le dernier commit. Cochez-le et faites un commit pour enregistrer les modifications.
A Ajouté (stagé)
Fichier dont les modifications ont été placées dans la zone de staging (l'index Git), prêt à être inclus dans le prochain commit. Peut être un nouveau fichier ou un fichier modifié explicitement stagé via le bouton Stager.
D Supprimé
Fichier qui existait dans le dernier commit mais qui a été supprimé. Le commit enregistrera cette suppression dans l'historique.
U Non suivi
Fichier présent sur le disque mais inconnu de Git. Il ne sera pas inclus dans les commits tant que vous ne le cochez pas. Vous pouvez aussi l'ajouter au .gitignore pour l'ignorer définitivement.
C Conflit
Fichier en conflit de fusion — Git n'a pas pu fusionner automatiquement les deux versions. Ouvrez le fichier, supprimez les marqueurs <<<<<<< / ======= / >>>>>>>, enregistrez, puis cochez et stagez le fichier pour marquer le conflit comme résolu.
Stash
Modifications temporairement mises de côté sans commit. Le compteur indique le nombre de stashes en attente. Utilisez Pop pour les restaurer.
Zone de staging (index)
La zone de staging est une zone intermédiaire entre vos fichiers et l'historique Git. Elle permet de choisir exactement ce qui entre dans le prochain commit, indépendamment de ce qui est modifié sur le disque.
Dans git-manager, le bouton Commit fait automatiquement git add sur les fichiers cochés — vous n'avez pas besoin de stager explicitement avant de commiter. Le bouton Stager est utile dans un cas précis : préparer un fichier pour un Amend sans commiter tout de suite.
Cas AM — si vous stagez un fichier puis le modifiez à nouveau sans commiter, il apparaît en A et M simultanément. Le prochain Commit inclura les deux zones ensemble — il n'est pas possible de les séparer.
Fichiers suivis
Le compteur Suivis dans le statut indique le nombre total de fichiers versionnés par Git. Ce sont les fichiers qui ont été committés au moins une fois et dont Git surveille les modifications.
Arrêter le suivi
Retirer un fichier du suivi Git le conserve sur le disque mais Git ne le versionne plus. Utile pour les fichiers de configuration locale.

Diff visuel

Cliquer sur un nom de fichier
Dans la section Fichiers modifiés — Diff & Commit, les fichiers M A D C ont leur nom souligné et cliquable. Cliquer ouvre une modale avec les modifications ligne par ligne — pour C, la modale indique si des marqueurs de conflit sont encore présents (bandeau orange) ou si le fichier est résolu (bandeau vert).
Les fichiers U ne sont pas cliquables — Git n'a rien à comparer.
Lecture du diff
Le tableau affiche 3 colonnes : numéro de ligne dans l'ancien fichier, numéro dans le nouveau, et le contenu.
Format d'une ligne :
12 12   ligne inchangée
13 − ancienne ligne
13 + nouvelle ligne
En-tête de bloc (hunk) :
@@ -97,6 +97,24 @@ switch ($action) {
-97,6 → ancien fichier : bloc à partir de la ligne 97, sur 6 lignes
+97,24 → nouveau fichier : même départ, sur 24 lignes (18 ajoutées)
switch ($action) { → contexte : le bloc de code englobant
Fichiers M et A — deux onglets possibles
Un fichier M ou A peut avoir des modifications dans deux zones :
Non stagé Modifications depuis le dernier git add — sera stagé au prochain Stager
Stagé Sera inclus dans le prochain Commit
Si les deux zones sont remplies, deux onglets apparaissent dans la modale.
Exemple pour obtenir les deux onglets :
1. Modifiez index.html et enregistrez
2. Cliquez Stager → le fichier passe en A
3. Modifiez à nouveau index.html et enregistrez — sans restager
4. Actualisez → le fichier apparaît en A et en M
5. Cliquez sur M → deux onglets Non stagé / Stagé
6. Cliquez sur A → deux onglets Non stagé / Stagé
Fichiers C — modale de conflit
Le titre de la modale indique l'état du fichier :
(conflits à résoudre) Bandeau orange — des marqueurs <<< sont encore présents
(conflit résolu) Bandeau vert — plus de marqueurs, prêt à stager
Le diff affiché (bandeau vert) montre la différence entre HEAD et votre version résolue — c'est ce qui ira dans le commit de fusion.

Récupération

HEAD
La version actuelle (dernier commit).
HEAD~1
La version du commit précédent.
HEAD~2
La version d'il y a 2 commits.
origin/main
La version sur GitHub (serveur distant).
4 façons de revenir en arrière :
Récupérer Restaure 1 fichier à une version précise Reste sur la branche
Checkout commit Explorer un ancien commit (tout le projet) HEAD détaché
Revert Annule un commit en créant un nouveau commit inverse N'écrase pas l'historique
Annuler tout Remet tous les fichiers modifiés au dernier commit Irréversible
Revert vs Checkout :
A → B → C → D  (main)
git checkout B → tu vois le code au moment de B, mais D existe toujours
git revert D → crée un commit E qui annule D :
A → B → C → D → E  (main)
git revert d'un revert → annule l'annulation (équivalent Ctrl+Y) :
A → B → C → Revert "C" → Revert "Revert C"
En cas de doute, utilisez le Stash pour sauvegarder vos modifications avant de revenir en arrière.

Avance / Retard

↑ Commits en avance
Commits locaux non encore envoyés sur GitHub. → Faire un Push
↓ Commits en retard
Commits sur GitHub non encore récupérés. → Faire un Pull
ex. 2 en avance :
PC: A→B→C→D→E
GitHub: A→B→C
ex. 2 en retard :
PC: A→B→C
GitHub: A→B→C→D→E
ex. Cas mixte (après un fetch ↑1 ↓2) :
PC: A→B→C→X
GitHub: A→B→C→Y→Z
→ Pull puis Push

Stash (Mettre de côté)

Mettre de côté
Sauvegarde temporairement vos modifications en cours sans faire de commit. Utile pour changer de branche rapidement ou tester quelque chose sur un code propre.
Pop (Restaurer)
Réapplique les modifications sauvegardées et supprime le stash. C'est l'action la plus courante.
Appliquer
Réapplique les modifications sauvegardées mais conserve le stash pour une utilisation ultérieure.
Supprimer un stash
Supprime définitivement un stash. Les modifications sauvegardées seront perdues.
Exemple :
1. Vous travaillez sur une feature, code pas fini
2. Urgence : corriger un bug sur main
3. Mettre de côté → vos modifications sont sauvegardées
4. Basculer sur main, corriger, commit, push
5. Revenir sur votre branche → Pop
6. Vos modifications sont de retour !

Tags

Tag léger
Simple pointeur vers un commit. Créé sans message. Utile pour un repère personnel.
Tag annoté
Objet Git à part entière avec un message, une date et l'auteur du tag. Recommandé pour les releases.
Push
Envoie le tag vers GitHub. Sans push, le tag reste local et n'est pas visible dans les releases GitHub. Pousser un tag déjà publié est sans effet.
Supprimer
Supprime le tag localement et tente automatiquement de le supprimer sur GitHub. Si le tag n'avait jamais été pushé, la suppression distante est ignorée silencieusement.
Convention MAJOR.MINOR.PATCH
· PATCH (+0.0.1) : correction de bug ou petit ajustement
· MINOR (+0.1.0) : nouvelle page ou fonctionnalité
· MAJOR (+1.0.0) : refonte architecturale ou visuelle importante
Créer une release pour un jalon significatif, pas pour chaque petit fix.

Actions dangereuses

Annuler toutes les modifications
Supprime TOUTES les modifications non committées. Irréversible !
Supprimer (dépôt + disque)
Supprime le fichier du dépôt ET de votre disque. Définitif !

Amend (modifier le dernier commit)

Bouton Amend
Modifie le dernier commit. Vous pouvez l'utiliser pour trois choses, seules ou combinées :
  • Ajouter des fichiers oubliés (cochez-les avant de cliquer Amend)
  • Changer le message (saisissez-en un nouveau dans le champ message avant de cliquer Amend)
  • Inclure des fichiers déjà stagés (ils sont pris automatiquement, sans avoir à les re-cocher)
Charger le message du dernier commit
Dans la section Historique des commits, le premier commit affiche un bouton crayon . Cliquez dessus pour charger le message complet (sujet et corps) dans le champ message — le champ prend le focus automatiquement. Modifiez-le, puis cliquez Amend.
Utile pour corriger une faute ou compléter la description sans retaper tout le message.
Commandes exécutées selon le cas :
# Ajouter un fichier oublié (sans changer le message)
git add fichier.txt
git commit --amend --no-edit
# Changer uniquement le message
git commit --amend -m "Nouveau message"
# Les deux à la fois
git add fichier.txt
git commit --amend -m "Nouveau message"
Exemples :
• Vous committez "Ajout du formulaire de contact" en oubliant style.css → cochez style.css et cliquez Amend
• Vous constatez une faute dans le message du dernier commit → corrigez-le dans le champ message et cliquez Amend (sans rien cocher)
• Vous avez déjà stagé un fichier via le bouton Stager → cliquez Amend directement, il est inclus automatiquement
• Vous voulez compléter le message du dernier commit sans tout retaper → cliquez dans l'Historique, modifiez le champ, puis cliquez Amend
Attention : L'amend réécrit le commit (nouveau hash). Si ce commit a déjà été pushé sur le remote, un git push --force sera nécessaire pour écraser l'ancien commit sur GitHub — l'interface vous en avertit automatiquement. À utiliser de préférence avant le Push, et uniquement sur une branche personnelle non partagée.

Fork (contribution)

Qu'est-ce qu'un fork ?
Une copie d'un dépôt GitHub vers votre propre compte. Permet de contribuer à un projet sans avoir les droits d'écriture ou créer votre propre version, le fork devient votre point de départ indépendant.
Dépôt original (autre utilisateur)
↓ Fork (sur GitHub)
Votre fork (votre compte GitHub)
↓ Clone
Votre PC (travail local)
↓ Push
Votre fork
↓ Pull Request
Dépôt original (proposition)
Le fork se fait sur GitHub.com (bouton "Fork"). Utilisez ensuite Cloner un dépôt pour récupérer votre fork.

Branches & Fusion de branches

Fusionner (Merge)
Le bouton bleu apparaît à côté des branches qui ne sont pas la branche en cours. Il intègre les commits de la branche sélectionnée dans la branche en cours.
Exemple :
Vous êtes sur main
Vous cliquez sur feature
→ Les commits de feature sont ajoutés à main
Workflow : Basculer sur main → Merge de feature → Push
Conflits de fusion
Si le même fichier a été modifié sur les deux branches :
Lignes différentes → Git fusionne automatiquement
Mêmes lignes → Conflit ! Git marque le fichier :
<<<<<<< HEAD
Code sur main
=======
Code sur feature
>>>>>>> feature
Résolution :
1. Ouvrir le fichier et choisir quelle version garder
2. Supprimer les marqueurs <<<, ===, >>>
3. Sauvegarder → Commit
Récupérer une branche distante
Cliquer sur une branche distante crée automatiquement une branche locale qui suit la branche distante et bascule dessus.
Cas d'usage : un collaborateur a poussé une nouvelle branche sur GitHub. Après un Fetch, elle apparaît dans "Branches distantes". Ce bouton la rapatrie en local en une seule action — sans avoir à créer la branche manuellement.
Supprimer une branche distante
Le bouton poubelle à côté des branches distantes permet de les supprimer directement sur GitHub.
Forcer le basculement
Si des fichiers non suivis bloquent le changement de branche, une option "Forcer" est proposée. Attention : les fichiers en conflit seront écrasés.
Renommer une branche
Le crayon permet de renommer une branche. Si la branche est publiée sur le remote, Git Manager renomme localement, publie le nouveau nom et supprime l'ancien automatiquement.
La branche par défaut (main ou master) ne peut pas être renommée car c'est la branche principale du dépôt distant.
Créer une branche :
Branche actuelle Copie avec historique
🆕 Branche vide Sans fichiers, sans historique
🔄 Nouveau départ Fichiers actuels, sans historique
Autre branche locale Démarre au dernier commit de cette branche — sans avoir à basculer dessus d'abord
origin/main (ou autre branche distante) Copie depuis le remote — état au dernier Fetch
Hash / ref (champ texte) Depuis un commit précis — prioritaire sur le menu Depuis si rempli
Pour utiliser le champ hash / ref : laisser le menu Depuis sur la première option et entrer le hash — il est prioritaire sur le menu si rempli.

HEAD détaché

Qu'est-ce que le HEAD détaché ?
Normalement, vous êtes toujours sur une branche (ex: main). Le HEAD détaché signifie que vous vous êtes placé directement sur un ancien commit, sans être sur aucune branche. C'est un mode d'exploration temporaire.
Se placer sur un commit
Dans l'historique des commits, cliquez sur le bouton à droite d'un commit pour vous y placer. Vous verrez vos fichiers tels qu'ils étaient à ce moment-là.
Créer une branche ici
Si le code vous convient, cliquez sur Créer une branche ici pour transformer cet état en branche officielle. Vous pourrez ensuite la fusionner où vous voulez.
Exemple de workflow :
1. Vous explorez l'historique et trouvez un ancien commit intéressant
2. Vous cliquez → Vous êtes en HEAD détaché
3. Vous vérifiez le code : il est parfait !
4. Vous cliquez Créer une branche ici → ex: ma-version
5. Maintenant ma-version est une branche officielle
6. Vous pouvez la fusionner dans main ou la publier sur GitHub
Pour revenir à la normale, basculez simplement sur une branche existante (ex: main).

Multi-dépôts

Sélecteur de dépôt
Menu déroulant affiché dans le header à côté du nom du dépôt courant. Permet de basculer entre plusieurs projets Git sans changer de virtual host.
Activation du sélecteur
Définir la clé reposRoot dans git-config.php avec le chemin absolu du dossier contenant vos projets. Si la clé est absente ou vide, le sélecteur n'est pas affiché.
Configuration dans git-config.php :
'reposRoot' => 'C:/Users/votre-nom/projets',
Structure attendue :
projets/
  ├── mon-site/ <- affiché dans le menu
  │ └── .git/
  ├── api-projet/ <- affiché dans le menu
  │ └── .git/
  └── dossier-sans-git/ <- ignoré
Seuls les sous-dossiers directs contenant un .git/ sont listés.
Si vous déplacez votre dossier de projets, pensez à mettre à jour le chemin reposRoot dans git-config.php.

Cloner un dépôt

Page de clonage
Permet de cloner un dépôt GitHub existant vers votre machine. Les fichiers Git Manager sont automatiquement copiés dans le nouveau dépôt.
Fichiers copiés :
git-manager.html, git-api.php, git-config.example.php, git-clone.html, git-reset-remote.html, git-auth.html, git-help.html, index.html, flavicon.svg
Sous-dossiers copiés intégralement : api/, css/, js/

Réinitialiser le dépôt distant

Page de réinitialisation
Crée une nouvelle branche vide (sans historique) et supprime les branches sélectionnées sur GitHub. Irréversible !

Authentification (SSH / Token)

Guide d'authentification
Configure l'accès à GitHub via SSH (clés) ou Token HTTPS. Nécessaire pour push/pull.
Cas d'usage :
  • Nettoyer un dépôt contenant des fichiers sensibles dans l'historique
  • Repartir de zéro sans supprimer/recréer le dépôt GitHub
  • Supprimer des branches obsolètes en masse

Retirer un fichier du dernier commit (avant push)

Le fichier est dans le dernier commit mais le push n'a pas encore été fait — l'amend est la solution propre.

  1. Section Supprimer un fichier du dépôt → sélectionner le fichier
  2. Cliquer Arrêter le suivi uniquement (conserve le fichier sur le disque) ou Supprimer (supprime aussi du disque)
  3. Le fichier apparaît en D dans la liste des fichiers modifiés
  4. Cocher le fichier, laisser le champ message vide, cliquer Amend
Le fichier est retiré du dernier commit sans créer un nouveau commit. Le message du commit original est conservé.

Statut A et M simultanés sur le même fichier

Vous stagez un fichier, puis vous le modifiez à nouveau sans commiter. Git suit deux états séparément — le fichier apparaît deux fois.

A Staging La version stagée — celle qui sera commitée si vous commitez maintenant
M Working tree La version actuelle sur disque — avec les nouvelles modifications
Si vous commitez maintenant, les modifications du working tree ne seront pas incluses — seule la version A partirait dans le commit.
Pour inclure les dernières modifications, il faut re-stager le fichier (bouton Stager ou git add), ce qui écrase le A avec le contenu actuel.

Résoudre un conflit de fusion

Un Pull ou un Merge a créé un conflit — Git n'a pas pu fusionner automatiquement un ou plusieurs fichiers.

  1. Le(s) fichier(s) en conflit apparaissent en C dans la liste des fichiers
  2. Cliquer sur le nom du fichier C → la modale indique l'état :
    • Bandeau orange → des marqueurs de conflit sont encore présents dans le fichier
    • Bandeau vert → le fichier est résolu, il reste à le stager
  3. Ouvrir le fichier dans votre éditeur de code
  4. Repérer les marqueurs et choisir la version à garder :
    <<<<<<< HEAD
    Version actuelle (votre branche)
    =======
    Version entrante (branche fusionnée)
    >>>>>>> feature
  5. Supprimer les trois marqueurs <<< === >>> et ne garder que le contenu voulu
  6. Sauvegarder le fichier
  7. Cliquer à nouveau sur le fichier dans git-manager → le bandeau doit passer au vert "Conflit résolu"
  8. Cocher le fichier, écrire un message si nécessaire, cliquer Commit pour finaliser la fusion
Notes :
  • Si plusieurs fichiers sont en C, répéter les étapes 3 à 7 pour chacun avant de commiter
  • Le diff affiché dans la modale (bandeau vert) montre la différence entre HEAD et votre version résolue. C'est exactement ce qui ira dans le commit de fusion. Le diff est juste et utile — il confirme quelle version vous avez gardée.
  • En cas de doute avant de commencer, utilisez le Stash pour sauvegarder votre état actuel

Changer de branche avec des modifications en cours

Toujours commiter ou stasher avant de changer de branche. Le Stash est exactement fait pour ça — un stash prend deux secondes et votre travail reste intact.

  1. Vous avez des modifications en cours sur main et devez basculer sur feature
  2. Cliquez Mettre de côté dans la section Stash — vos modifications sont sauvegardées
  3. Basculez sur feature — le working tree est propre, aucun risque d'écrasement
  4. Travaillez sur feature, commitez si nécessaire
  5. Revenez sur main → cliquez Pop — vos modifications sont restaurées
Ce qui arrive si vous ne le faites pas : Git tente d'emporter vos modifications non commitées vers la branche cible. Si la branche cible a ses propres versions commitées des mêmes fichiers, Git écrase silencieusement votre working tree au retour — les modifications sont perdues sans avertissement.

Workflow typique

  1. Modifier vos fichiers dans votre éditeur de code
  2. Vérifier les changements dans la section "Fichiers modifiés" — vos fichiers apparaissent avec le statut M (modifié), A (ajouté), U (non suivi), D (supprimé) ou C (conflit).
  3. Cocher les fichiers à inclure dans le commit — le git add se fait automatiquement au moment du commit
  4. Écrire un message clair décrivant les changements (ex: "Ajout du formulaire de contact")
  5. Commit pour enregistrer un instantané de vos fichiers stagés dans l'historique local
  6. Push pour envoyer vos commits vers GitHub et les partager
Bon à savoir :
  • Fetch avant de travailler pour récupérer les dernières modifications distantes
  • Pull pour fusionner les modifications distantes dans votre branche locale
  • Un commit reste local tant que vous n'avez pas fait de Push

Exercice — Premier commit

Créer le tout premier commit d'un dépôt.

  1. Ouvrir git-manager et sélectionner le dépôt
  2. Dans la zone de staging, repérer les fichiers en statut U (non suivis)
  3. Cocher les fichiers à inclure (ex : CLAUDE.md et .gitignore)
  4. Écrire le message : Initial commit
  5. Valider le commit
Ce qu'on observe :
  • Statut avant staging : U (Untracked)
  • Statut après staging : A (Added)
  • root-commit dans la sortie → premier commit du dépôt, sans parent
  • Le hash (ex : d21c8ce) identifie ce commit de façon unique

Exercice — Modifier un fichier et observer les statuts

Comprendre la zone de staging en observant les statuts en temps réel.

  1. Créer un nouveau fichier (ex : niveau-1/notes.md)
  2. Observer son statut dans git-manager : U
  3. Le stager → statut passe à A
  4. Modifier le fichier sans le re-stager
  5. Observer : le fichier apparaît en A ET en M simultanément
  6. Re-stager pour inclure les dernières modifications
  7. Commiter : feat: add niveau-1 notes
Ce qu'on observe : le même fichier apparaît deux fois parce que Git suit deux états séparément.
StatutZoneCe que ça représente
AStagingLa version stagée — celle qui sera commitée si tu commites maintenant
MWorking treeLa version actuelle sur disque — avec ta nouvelle modification

Si tu commites maintenant, ta dernière modification ne sera pas incluse — seule la version A (l'ancienne) partirait dans le commit. Pour inclure la modification, il faut re-stager le fichier (bouton Stager ou git add), ce qui écrase le A avec le contenu actuel.

Exercice — Lire un diff

Comprendre ce que Git affiche quand un fichier est modifié.

  1. Modifier un fichier déjà commité (ajouter ou supprimer quelques lignes)
  2. Dans git-manager, repérer le fichier en statut M
  3. Cliquer sur son nom pour ouvrir la vue diff
  4. Identifier dans le diff :
    • L'en-tête @@ -x,y +x,y @@ → numéro de ligne et nombre de lignes dans l'ancien/nouveau fichier
    • Les lignes + en vert → lignes ajoutées
    • Les lignes - en rouge → lignes supprimées
    • Les lignes sans signe → contexte inchangé
Exemple : @@ -26,3 +26,11 @@ → bloc à partir de la ligne 26 ; 3 lignes avant, 11 après (8 lignes ajoutées).

Exercice — Amend

Corriger un message oublié ou ajouter un fichier oublié dans le dernier commit.

Corriger le message :
  1. Faire un commit avec un message volontairement mauvais (ex : fix: notes)
  2. Dans git-manager, charger le message via le crayon ✏️ dans l'historique
  3. Corriger le message dans le champ
  4. Cliquer Amend (sans rien cocher)
  5. Vérifier dans l'historique que le message a changé — et que le hash a changé
Ajouter un fichier oublié :
  1. Faire un commit en oubliant volontairement un fichier
  2. Ne pas toucher au champ message
  3. Cocher le fichier oublié dans la liste
  4. Cliquer Amend
  5. Vérifier que le fichier est maintenant dans le commit
À retenir : l'amend réécrit le commit (nouveau hash). Ne jamais amender un commit déjà pushé sur une branche partagée.

Exercice — Créer une branche, commiter, fusionner

Comprendre le cycle de vie d'une branche feature.

  1. Créer une branche depuis main : bouton Créer → nommer feature-nom
  2. Basculer sur cette branche, faire un ou plusieurs commits
  3. Revenir sur main
  4. Fusionner : cliquer le bouton sur la ligne de feature-nom
  5. Supprimer la branche une fois fusionnée

Ce qu'on observe :

  • Fast-forward : si main n'a pas bougé pendant le travail sur la branche, Git avance simplement le pointeur — aucun commit de fusion créé
  • Merge commit : si main a reçu un commit pendant qu'on travaillait sur la branche, les deux branches ont divergé. Git crée alors un commit de fusion qui réconcilie les deux — il apparaît dans l'historique avec deux lignes entrantes
Un merge commit n'implique pas forcément un conflit. Si les deux branches ont touché des fichiers différents — ou des parties différentes des mêmes fichiers — Git fusionne automatiquement. Le conflit n'arrive que si les deux branches ont modifié les mêmes lignes du même fichier.

Exercice — Provoquer et résoudre un conflit

Comprendre pourquoi un conflit se produit et comment le résoudre.

Prérequis : avoir un fichier commité sur main.

Créer le conflit :
  1. S'assurer d'être sur main
  2. Créer la branche conflit-test et basculer dessus
  3. Sur conflit-test : modifier la ligne 1 du fichier → commiter
  4. Revenir sur main
  5. Sur main : modifier la même ligne 1 → commiter
  6. Fusionner conflit-test dans main
Résoudre le conflit :
  1. Faire un Refresh — le fichier en conflit apparaît avec le statut C dans la liste
  2. Ouvrir le fichier — Git a inséré des marqueurs :
<<<<<<< HEAD
# Titre (version main)
=======
# Titre (version conflit-test)
>>>>>>> conflit-test
  1. Choisir quelle version garder (ou écrire une version combinée)
  2. Supprimer les marqueurs <<<<<<<, =======, >>>>>>>
  3. Sauvegarder — cliquer le nom du fichier dans git-manager : le bandeau passe au vert
  4. Stager le fichier puis commiter

Ce qu'on observe :

  • Le commit de résolution est un merge commit (deux parents visibles dans l'historique)
  • Pendant la résolution, le fichier peut apparaître avec les statuts C et M simultanément — c'est normal
Piège fréquent : il faut impérativement commiter sur main après avoir créé conflit-test. Sans ce commit sur main, Git fait un fast-forward au lieu d'un conflit.

Exercice — HEAD détaché

Explorer un ancien commit sans modifier l'historique.

  1. Dans l'historique, cliquer sur un ancien commit puis Checkout — Git se place sur ce commit en mode HEAD détaché
  2. Observer : aucune branche n'est active, les fichiers correspondent à l'état exact de ce commit (les fichiers créés après ce commit ont disparu du dossier)
  3. Pour revenir à la normale : cliquer sur la ligne de main dans la liste des branches

Ce qu'on peut faire depuis un HEAD détaché :

  • Consulter le code à un instant passé, copier des fichiers
  • Cliquer Créer une branche ici pour transformer cet état en branche officielle et y commiter
Tout commit fait en HEAD détaché sans créer de branche est inaccessible une fois qu'on change de branche — Git ne le supprime pas immédiatement mais il n'apparaît plus dans aucun historique.

Exercice — Créer une branche depuis un commit précis (hash)

Créer une branche qui repart exactement d'un état passé, sans passer par le HEAD détaché.

Prérequis : avoir au moins 3 commits sur main.

  1. Dans la section Historique, noter le hash d'un commit ancien (ex : a3f9c12) en cliquant pour vérifier son contenu
  2. Dans la section Branches, laisser le menu Depuis sur la première option
  3. Saisir le hash dans le champ ou hash / ref...
  4. Entrer un nom de branche (ex : hotfix-ancien) → cliquer Créer
  5. Basculer sur hotfix-ancien — les fichiers correspondent à l'état exact du commit choisi
Différence avec le HEAD détaché : le HEAD détaché place Git sur un commit sans branche — tout commit y est perdu si on repart. Créer une branche depuis un hash crée directement une branche stable depuis ce point, sans passer par l'état détaché.
Cas d'usage : corriger un bug introduit il y a plusieurs commits sans toucher à main — on crée une branche depuis le commit juste avant le bug, on corrige, puis on merge.

Exercice — Simuler un travail à deux

Comprendre comment récupérer des modifications faites par quelqu'un d'autre (ou directement depuis GitHub).

  1. Sur GitHub, ouvrir un fichier et le modifier via l'interface web → commiter
  2. En local, cliquer Fetch → observer ↓1 sur la branche
  3. Cliquer Pull sans cocher --rebase → le commit distant arrive en local

Ce qu'on observe :

  • Fetch met à jour origin/main sans toucher à main locale — le compteur ↓ indique qu'il y a des commits à récupérer
  • Pull fusionne origin/main dans main locale
Pull classique vs pull --rebase :
Sans --rebase : Git fait un merge entre le distant et le local. Si les deux ont divergé, un merge commit est créé — l'historique montre une fourche qui se referme.
Avec --rebase : Git retire temporairement tes commits locaux, avance sur les commits distants, puis rejoue tes commits par-dessus. Résultat : un historique linéaire, comme si tu avais travaillé après le commit distant. Tes commits sont réécrits (nouveaux hash).
Règle pratique : --rebase pour garder un historique propre sur une branche personnelle — pull classique sur une branche partagée (réécrire des commits déjà pushés crée des conflits pour les autres).

Exercice — Conflit local/distant avec pull --rebase

Comprendre la différence entre pull classique et pull --rebase, et résoudre un conflit de synchronisation.

  1. Modifier une ligne d'un fichier en local → commiter (sans pusher)
  2. Modifier la même ligne directement sur GitHub → commiter
  3. En local, cliquer Pull avec l'option --rebase activée → conflit
  4. Faire un Refresh — les fichiers en conflit apparaissent avec le statut C dans la liste
  5. Ouvrir le fichier conflictuel, résoudre, supprimer les marqueurs, sauvegarder
  6. Stager le fichier dans git-manager — idéalement sans commiter : c'est Continuer qui rejoue le commit original. Commiter avant fonctionne aussi mais crée un commit supplémentaire dans l'historique
  7. Dans le panneau Branches, un banner bleu Rebase en cours apparaît → cliquer Continuer
  8. Pusher

Ce qu'on observe :

  • Pendant le rebase, git-manager affiche "Rebase en cours" en bleu dans le statut et dans le panneau Branches
  • Le résultat est un historique linéaire : pas de commit de fusion, l'historique est plus lisible
pull vs pull --rebase :
pull classique → crée un commit de fusion avec deux parents
pull --rebase → rejoue le commit local après le commit distant, pas de merge commit
Continuer : finalise le rebase en rejouant le commit original avec le contenu résolu. Le fichier conflictuel doit être stagé au préalable.
Abandonner : annule le rebase et ramène le dépôt exactement à l'état qu'il avait avant le pull --rebase — tes commits locaux sont restaurés, les commits distants ne sont pas intégrés. Utile si le conflit est trop complexe ou si tu veux recommencer autrement.

Exercice — Stash

Mettre de côté des modifications en cours pour changer de contexte sans perdre son travail.

Partie 1 — Stash basique :
  1. Modifier un fichier sans commiter — il apparaît en M
  2. Cliquer Mettre de côté → saisir un message descriptif (ex : wip: ajout ligne notes) — la case + non suivis inclut les fichiers U dans le stash si elle est cochée
  3. Observer : le fichier M disparaît, le compteur Stash passe à 1
  4. Basculer sur une autre branche — working tree propre, aucun risque
  5. Revenir sur main → cliquer Pop — modifications restaurées, stash supprimé
Partie 2 — Plusieurs stashes :
  1. Modifier un premier fichier (ex : notes.md) → Mettre de côté avec le message wip: modification A
  2. Modifier un second fichier (ex : CLAUDE.md) → Mettre de côté avec le message wip: modification B
  3. Cliquer Appliquer sur le stash A (notes.md) → modifications restaurées, stash A conservé dans la liste
  4. Cliquer Pop sur le stash B (CLAUDE.md) → modifications restaurées et stash B supprimé
  5. Cliquer Supprimer sur le stash A restant — il a déjà été appliqué, on peut le jeter
Appliquer ≠ Pop : Appliquer restaure les modifications en conservant le stash — utile pour appliquer le même stash sur plusieurs branches. Pop restaure et supprime en une seule opération.
Piège : ne pas faire Pop sur un stash qui vient d'être Appliqué — le fichier est déjà dans le working tree, Git ne peut pas l'écraser et retourne une erreur.
Partie 3 — Stash avant changement de branche (règle fondamentale) :
  1. Modifier un fichier sur main sans commiter
  2. Tenter de basculer sur une autre branche sans stasher — observer le comportement
  3. Revenir sur main, stasher les modifications
  4. Basculer sur l'autre branche, faire un commit, revenir sur main
  5. Pop → continuer le travail interrompu
Piège : si les modifications n'entrent pas en conflit avec la branche cible, Git les emporte silencieusement — les fichiers "voyagent" avec le HEAD sans avertissement. On croit le working tree propre alors qu'il ne l'est pas. Le stash est la seule garantie.

Exercice — Revert d'un commit

Comprendre qu'annuler un commit ne supprime pas l'historique — Git crée un nouveau commit inverse.

Prérequis : avoir un fichier (ex: notes.md) avec du contenu déjà commité.

  1. Faire un commit volontairement "mauvais" (ex : supprimer une ligne dans notes.md → message bug: suppression accidentelle)
  2. Dans l'historique, cliquer sur ce commit → bouton Revert
  3. Confirmer — git-manager crée un commit inverse automatiquement
  4. Vérifier que le fichier est revenu à son état d'avant

Ce qu'on observe :

  • L'historique montre désormais deux commits : le mauvais ET le revert — rien n'est effacé
  • Fonctionne que le commit soit pushé ou non — indispensable quand il est déjà pushé car c'est la seule façon d'annuler sans réécrire l'historique partagé
Revert vs Reset :
revert → crée un commit inverse, safe sur une branche partagée
reset --hard → réécrit l'historique, dangereux si déjà pushé (force push requis) — non disponible dans git-manager, requiert le terminal
push --force n'est pas non plus disponible dans git-manager — réécrire l'historique partagé écrase les commits des autres collaborateurs sur le remote et peut causer des pertes de travail irréversibles.

Exercice — Récupérer un fichier depuis un commit précis

Restaurer un fichier à une version antérieure sans toucher aux autres fichiers.

  1. Dans la section Récupérer un fichier, sélectionner (ex: notes.md) — deux zones apparaissent : l'accès rapide et la liste des commits
  2. Via l'accès rapide : choisir ex: HEAD~1 → cliquer Récupérer
  3. Ou via la liste Commits pour ce fichier : cliquer le bouton sur la ligne du commit voulu
  4. Le fichier apparaît avec le badge A dans la liste (stagé directement) — cliquer sur son nom pour vérifier le diff
  5. Commiter la restauration avec un message explicite (ex : restore: notes.md version HEAD~1)
La récupération ne crée pas de commit automatiquement — le fichier est stagé A prêt à commiter.
Si git-manager affiche "Le fichier à ce commit est identique à la version actuelle", le commit sélectionné n'a rien changé — choisir un commit plus ancien dans la liste.
Le commit de restauration est annulable comme n'importe quel autre : un Revert dessus remet le fichier dans l'état d'avant la récupération.

Exercice — Utiliser l'historique par fichier

Retrouver à quel commit une modification précise a été introduite, puis restaurer la version antérieure.

  1. Dans la section Récupérer un fichier, sélectionner (ex: notes.md)
  2. La liste Commits pour ce fichier apparaît — elle ne montre que les commits qui ont modifié ce fichier (plus court que l'historique global)
  3. Pour chaque commit : cliquer pour voir le détail (fichiers modifiés, contenu)
  4. Identifier le commit qui a introduit la ligne à annuler
  5. Cliquer sur le commit juste en dessous (le précédent dans la liste) — c'est la version d'avant la modification
  6. Vérifier le diff → commiter la restauration
Le premier commit de la liste (le plus récent) a toujours le même contenu que la version actuelle — le sélectionner ne produit aucun changement visible.
Piège : un revert crée un nouveau commit dans l'historique par fichier — si on a reverté notes.md, il apparaîtra deux fois pour le même contenu dans la liste.

Exercice — Annuler toutes les modifications

Remettre tous les fichiers modifiés à l'état du dernier commit en une seule opération.

  1. Faire des modifications sur plusieurs fichiers sans commiter
  2. Dans la section Fichiers modifiés — Diff & Commit, cliquer Annuler toutes les modifications (en bas de la section)
  3. Confirmer — tous les fichiers M reviennent à leur version du dernier commit
Irréversible — cette opération équivaut à git checkout -- . : toutes les modifications non commitées sont perdues définitivement. Les fichiers U (non suivis) ne sont pas touchés.
Différence avec Récupérer un fichier : les deux sections sont séparées — "Récupérer un fichier" cible un seul fichier et peut aller chercher une version ancienne. "Annuler toutes les modifications" est dans la section Fichiers modifiés et remet tout à HEAD en une seule fois — utile pour repartir d'un état propre quand les modifications en cours ne valent pas la peine d'être gardées.

Exercice — Récupérer un fichier depuis le remote

Restaurer un fichier à la version qui se trouve sur GitHub, en ignorant les commits locaux.

Prérequis : un dépôt avec remote configuré (ex: notes.md) commité et pushé.

  1. Modifier (ex: notes.md) en local → commiter (sans pusher)
  2. Faire un Fetch pour s'assurer qu'origin/main est à jour
  3. Dans la section Récupérer un fichier, sélectionner notes.md
  4. Dans l'accès rapide, choisir origin/main (distant) → cliquer Récupérer
  5. Le fichier revient à la version pushée — badge A dans la liste
  6. Commiter la restauration (ex : restore: notes.md depuis origin/main)
origin/main vs HEAD~1 : HEAD~1 recule d'un commit local. origin/main ramène la version du remote — si tu as fait 3 commits locaux non pushés sur ce fichier, origin/main recule de 3 d'un coup, HEAD~1 d'un seul.
Fetch obligatoire avant d'utiliser origin/main — sans Fetch récent, la version récupérée peut être obsolète si quelqu'un a pushé depuis.
Même résultat avec Revert ? Pas tout à fait — Revert annule un commit entier (tous les fichiers qu'il touchait). origin/main cible un seul fichier et l'amène à la version exacte du remote, indépendamment des autres fichiers du commit.

Exercice — Tags annotés et release GitHub

Marquer une version stable avec un tag annoté et la publier sur GitHub.

Prérequis : avoir main avec plusieurs commits et un remote configuré.

  1. Dans la section Tags, saisir le nom du tag (ex : v1.0) et un message (ex : Première version stable) → cliquer Créer
  2. Observer : le tag apparaît dans la liste avec son message et la date
  3. Cliquer Pousser sur le tag — il est envoyé sur GitHub
  4. Sur GitHub, aller dans Releases → le tag est visible comme release
Tag annoté vs tag léger :
Un tag annoté contient un message, une date et l'auteur — c'est un objet Git à part entière, recommandé pour les releases.
Un tag léger est juste un pointeur vers un commit, sans métadonnées — utile pour marquer un point temporaire en local.
Supprimer un tag : le bouton supprime le tag localement et tente automatiquement de le supprimer sur GitHub. Si le tag n'avait jamais été pushé, la suppression distante est ignorée silencieusement.

Exercice — Branches simultanées (hotfix + feature en parallèle)

Gérer un correctif urgent sans interrompre un travail en cours sur une autre branche.

Prérequis : avoir main avec du contenu commité.

  1. Créer feature/ajout depuis main → y faire 1 ou 2 commits
  2. Réaliser qu'il y a un bug urgent sur main — stasher les modifications en cours si besoin
  3. Créer hotfix/bug depuis main (menu Depuis → sélectionner main)
  4. Corriger le bug sur hotfix/bug → commiter
  5. Basculer sur main → fusionner hotfix/bug → pusher
  6. Supprimer hotfix/bug
  7. Revenir sur feature/ajout → fusionner main pour récupérer le correctif
  8. Continuer le travail sur feature/ajout → merger sur main quand terminé
Principe : main reste toujours stable — les hotfix partent de main et y reviennent directement. Les features partent aussi de main mais vivent plus longtemps. Le merge de main dans feature (étape 7) évite un conflit important lors du merge final.
Piège : créer hotfix/bug depuis feature/ajout au lieu de main — le hotfix embarquerait alors les commits de la feature, et le merge sur main introduirait du code non validé.

Exercice — Multi-dépôts

Gérer plusieurs projets depuis une seule interface git-manager.

Prérequis : avoir reposRoot configuré dans git-config.php avec le dossier parent contenant vos dépôts.

  1. Ouvrir git-manager — si reposRoot est configuré, un sélecteur de dépôts apparaît dans l'en-tête
  2. Sélectionner un autre dépôt dans le menu déroulant — l'interface bascule sur ce dépôt (statut, branches, historique)
  3. Faire un commit sur ce dépôt → revenir sur le premier via le sélecteur
  4. Observer : chaque sélection recharge complètement l'interface pour le dépôt choisi
Configuration : dans git-config.php, définir reposRoot avec le chemin du dossier qui contient vos dépôts. git-manager scanne ce dossier et liste tous les sous-dossiers qui contiennent un .git/.

Navigation : les pages secondaires (Clone, Auth…) conservent le dépôt actif via le paramètre ?repo= dans l'URL — le bouton Retour ramène toujours sur le bon dépôt.
